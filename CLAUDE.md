# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow: every new piece of work starts in a fresh worktree

Before starting anything new (a shop, a car, a fix, a refactor), first make the main checkout clean and current (`git status` clean, `git pull --ff-only` on `main`), then create a new worktree for it (`git worktree add .worktrees/<branch> -b <branch>`) and do all the work there. Never start new work, or leave it uncommitted, in the main checkout. Symlink `.venv`, `filaments/sources` and `filaments/.cache` into the worktree from the main checkout.

**Git rules (the user set these; they override any "push when done" habit).**
- Free to do without asking: commit, push to a feature branch, `git pull --ff-only` on `main`, create worktrees.
- **Always ask first, every time, before anything lands on `main`**: `git push origin <branch>:main`, merging into `main`, or any push to `main`. Pushing to `main` publishes the live GitHub Pages site (CI deploys on push), so it is outward-facing. An earlier "yes, push" does not cover a later change, and a request like "add X to the page" is not a request to publish it. Build, commit on the branch, show the result (local preview), then ask.
- **Every feature, fix or doc change gets its own worktree**, no exceptions for small edits (CLAUDE.md edits included). Never commit in the main checkout.

**Colours are shown as images, never as hex alone.** Whenever you give the user a colour code (a measured chip, a filament, an override, a before/after, a palette), show it as a rendered swatch the user can look at: a local preview page in a Terminal panel tab (swatch + name + year/code + hex, next to the source chip or photo where there is one), or an inline widget/image. A bare `#1E4A30` in the reply is not enough. When a colour was overridden, show the old and new swatch side by side.

## Commands

Always use the in-project venv (`./.venv/bin/python`), never the system Python or `~/.venvs/hudson/` from the project's earlier life.

```bash
# One-off setup after a fresh clone
python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt

# Full rebuild for one car (measures swatches, measures all filaments, matches, thumbnails, HTML)
scripts/rebuild.sh <car_name>              # defaults to doppler

# HTML-only rebuild (after a filaments.json tweak, build_html.py styling, or car.json edit)
scripts/rebuild_html_only.sh <car_name>

# Publish: commit cars/<car>/output and push; .github/workflows/pages.yml deploys (asks first: it pushes)
scripts/publish.sh <car_name>

# Fetch the filament catalog from every shop in shops/*.yaml (polite + cached; first run is slow)
scripts/fetch_all_shops.sh                 # extra args: --shop <key>, --dry-run, --refresh, --force

# Unit tests (shoplib: rules, finish ban, sitemap, extraction — no network)
.venv/bin/python -m unittest discover -s tests

# Run one stage manually
.venv/bin/python src/<stage>.py --car <car_name>
```

Only `src/shoplib.py` has unit tests. Everything else is verified manually: open `cars/<name>/output/<name>.html` in a browser (or republish the Claude artifact) and check that the primary filament picks look right against the car swatches.

## Architecture

**Two data worlds, one pipeline.** The project matches a car's paint catalog against a filament catalog. The filament catalog is global (one shared pool serves every car); the paint catalog is per-car. The folder layout mirrors that split exactly:

- `filaments/{sources,data}/` — shared product photos and the single `filaments.json`.
- `cars/<name>/{sources,data,output}/` + `car.json` + `card_layout.json` — everything specific to one paint source.

Every script that needs paths imports `src/config.py`, which exposes `FILAMENTS_SOURCES`, `FILAMENTS_JSON`, and `car_sources(name) / car_data(name) / car_output(name) / car_meta(name)`. Nothing else should hard-code paths. `DEFAULT_CAR` reads the `CAR` env var and falls back to `doppler`.

**Pipeline stages, in order:**

1. `fetch_all.py` (one `shops/<shop>.yaml` per shop) → `filaments/data/filaments_raw_<shop>.json` + photos in `filaments/sources/`, plus `catalog.lock.json` and `fetch_report.json`.
2. `measure_filaments.py` globs **every** `filaments_raw*.json`, drops banned finishes, measures each image, stamps `regions` from the shop's YAML, dedupes by (URL, slug) → `filaments/data/filaments.json`
3. `measure_car.py --car <name>` reads `cars/<name>/card_layout.json` (per-swatch cx/cy coordinates), crops each sample from its card scan, writes `cars/<name>/data/car_colors.json`
4. `compute_matches.py --car <name>` → top-K PLA + PETG + ASA per color via ΔE2000, per region
5. `prepare_thumbnails.py --car <name>` → inline base64 JPEGs of the filament photos (self-contained HTML)
6. `prepare_hero.py --car <name>` → `cars/<name>/data/hero.json` (optional, only when `car.json` has `hero`; see below)
7. `build_html.py --car <name>` → `cars/<name>/output/<name>.html`

**Adding a new car** must not require editing any code in `src/`. The whole per-car customization is: `cars/<new_name>/car.json` (display name, tagline, years, source URL template, badge label), `cars/<new_name>/card_layout.json` (card images + swatch coordinates), and the card scans in `cars/<new_name>/sources/`. Then `scripts/rebuild.sh <new_name>`. Keep this contract — if a new car requires a code change, that's a bug in the generic pipeline, not a reason to special-case the car.

**New-car checklist: every item, so nothing is missed.** Do all of these in one go; the finish line is the commit on its branch; the push to `main` waits for the user's go-ahead (see Git rules).
1. Work in a git worktree (`.worktrees/<branch>`, gitignored); symlink `.venv`, `filaments/sources` and `filaments/.cache` from the main checkout.2. `cars/<name>/car.json` (years newest-first, `pages_per_year`, URL patterns), then `scripts/fetch_car_cards.sh <name>` (ask the user before downloading).
3. `card_layout.json`: pick only the chips that belong to the model; cards with smaller chips set `box_width`/`box_height` per card. Check the boxes on an overlay image before measuring.
4. `scripts/rebuild.sh <name>`, unit tests, and show the user the sampling preview and the HTML page (check both region views) before pushing.
5. **README.md "Current cars" table**: add or update the car's row (years, page link; no colour counts).
6. **Publish**: `"publish": true` in `car.json` (only when the user wants it live), plus `"index": {"color": ...}` (the tile's resting colour, chosen by the user) and **its own theme**: `"theme": "<name>"` in `car.json` with `themes/<name>/tile.css` + `tile.html`. A car without `theme` falls back to `doppler` and would share Doppler's look *and* its layout-editor offsets/colours (they are saved per theme, not per car). Run `src/build_index.py` and commit `site/index.html`; there is no hand-written list of cars on the site.
7. Ask the user, then push to `main` (never without a yes). The `pages` workflow deploys on its own: do not wait for it or check the build/live page unless the user asks.
7a. **Hero**: prepare it as described under "Recolor preview" (full-size photo, `hero_assets.json`, `make_hero_assets.py`); a low-res or colour-keyed-only hero is the most common reason a car's preview looks bad.
8. Update the car list in this file ("Current shops"-style docs) if it names cars, and say in the reply what was not done.
9. The main checkout may be on another branch with someone else's uncommitted work: never commit there. Use a worktree on `origin/main` to commit; push to `main` only after the user says so.
10. **Previews from a worktree need a local server.** Whenever the user wants to see the result of work done in a worktree, start a local server in a Terminal panel tab (`run_in_terminal`), e.g. `.venv/bin/python scripts/serve_preview.py .worktrees/<branch>/cars/<car>/output <port>` (a no-cache server: plain `http.server` lets Chrome keep showing the old page after a rebuild), and give the user the `http://localhost:<port>/<car>.html` link to open in Chrome. Don't just hand over a file path.

**Adding a new shop** must not require code either, if its platform is known: write `shops/<key>.yaml` (`name`, `platform`, **`regions`**, `base`, `sitemap`, `include` regex for product URLs), run `src/fetch_all.py --shop <key> --dry-run` to check the candidate list, then a real run. Add a `.shop-tag.shop-<slugified name>` CSS block in `build_html.py`. Platforms (`src/adapters/`): `upgates` / `shoptet` / `generic` = sitemap + one product page each (JSON-LD → microdata → `<h1>`/og); `shopify` = `/products.json`; `manual` = only `pins:`. A shop on a new platform that has a sitemap and schema.org markup works as `generic`. Record shape downstream: `{slug, brand, material, color_name, shop, url, image_url, local_image, availability, stock, title, last_ok, stale?}` (no `price`, see below).

Current shops (`shops/*.yaml`): Smart3D, Aurapol, Hubacek3D (upgates); 3DFox (shoptet, **3dfoxshop.cz**, not 3dfox.cz); Fillamentum (shopify); FilamentPM, 3DJake (generic, 3DJake limited to Fiberlogy because of its 10 s Crawl-delay); Prusa3D, Na3D, Bambu Lab (manual — Prusa's and Bambu's sitemaps only have parent pages, the colour is a variant). Polymaker, Spectrum (US storefront) and Overture (all shopify, `[int]`) keep colours as variants, so their YAML has `split_variants: {option: Color, keep: <regex on variant title>}` (one record per colour, the variant's own photo, never the product's first image; multicolour spools with plain names are excluded by hand via `exclude`; Spectrum's `color_strip` regex drops line prefixes from derived colour names). Regions: Prusa3D and Bambu Lab = `[eu, int]` (they sell in both), Polymaker, Spectrum and Overture = `[int]`, every other shop = `[eu]`.

**Bambu Lab pins** (`shops/bambulab.yaml`, EU store, a Next.js app: no `/products.json`) are generated from the colour selector on each parent page (`<li value="Jade White (10100)">` → `<img src=swatch>`, in `property_selector_Color`). `image_url` is the store's flat colour swatch, which measures exactly. Only single-colour lines are pinned (PLA Basic / Matte / Tough+ / Pure / Metal / Sparkle, PETG Basic / HF / Matte); Marble, Galaxy, Aero, Gradient, Silk, Translucent, CF, Glow and Wood are left out. White swatches are pure #FFFFFF and read as background, so they have manual overrides in `color_overrides.json`.

**No prices, anywhere.** The pipeline deliberately does not scrape, store, hard-code, or display filament prices. That covers no `extract_price()` in fetchers, no `price` key in any record or JSON, no price columns in fetcher logs, and no prices or currency in the HTML. Prices change constantly, discounts make them wrong within days, and the old hard-coded "749 Kč" for Prusament was already stale. The shop link on each candidate is the source of truth. Don't add prices back when writing a new fetcher or touching `build_html.py`.

**Regions, one page.** Every shop lists the regions it sells in (`regions: [eu]` in `shops/<key>.yaml`; the keys and labels live in `regions:` of `shops/_defaults.yaml`, currently `eu` = "EU / CZ" and `int` = "INT"). A shop can list several, and adding a region (e.g. `us`) is one defaults entry plus tagging shops, no code. `shoplib.ShopRules` refuses a shop without a known, non-empty `regions:`. `measure_filaments.py` copies the shop's regions onto each record (`regions: [..]`, looked up by shop name, so a region edit only needs a re-measure, not a refetch). `compute_matches.py` writes `cars/<car>/data/matches.json` as `{region: [colour + pla/petg/asa candidates]}`; `prepare_thumbnails.py` writes one `thumbnails.json`; `build_html.py` writes ONE `output/<car>.html` with an EU / CZ ↔ INT switch (`body[data-region]`, `?region=int` in the URL, per-region header counts). Regions never mix in one candidate list: a filament shows under every region of its shop. INT currently = Prusa3D (Prusament), Bambu Lab (both also in EU / CZ), Polymaker, Spectrum and Overture. There is no `-intl.html` any more; `build_site.sh` writes `<car>/intl.html` as a redirect to `?region=int` so old links work.

**Candidate rows are minimal.** Each row is swatch + name + ΔE. Photo, HEX, shop tag and shop link live in one shared hover/focus/tap bubble (`TIP_JS` in `build_html.py`, data from `data-*` on `.pick`); photos are embedded once in a slug→data-URI map. Click on swatch or name recolours the preview.

## Colour calibration against real-car photos (optional per car, `src/calibrate_car.py`)

Card scans age and fade, so a chip can sit far from the real paint (Sakura's Universal Blue measured near navy, ΔE 23 off the real car). Per car, `cars/<car>/calibration.json` lists photos of real cars per paint code (`car_code`, optional `year`, `note`; per photo `file`, `url`, `bbox` = body area in photo pixels, `mode` = `["hue", lo, hi, min_sat, min_v, max_v]` for coloured paint or `["neutral", max_sat, min_v]` for white/silver). Photos live in `cars/<car>/sources/photos/` (gitignored, third-party; `--fetch` re-downloads them from `url`, ask the user before downloading).
- `calibrate_car.py --car <name>`: samples each photo (median and brighter half of the selected body pixels), writes `data/calibration.json` and a self-contained `data/calibration_report.html` (card chip, picked-now chip, photo samples, the photos with the sampled pixels shown, suggested colour = mean of the photo medians, ΔE card→suggested; colours without a manifest entry are listed as chips). `--pdf FILE` prints it with headless Chrome.
- `--apply` writes the suggestion as `hex` + `hex_note` on the matching swatches of `card_layout.json` (all years of that code); `measure_car.py` then uses it and keeps the scan value as `measured_hex`. Then run `measure_car.py`, `compute_matches.py`, `prepare_thumbnails.py`, `build_html.py`.
- Finding photos is the manual part: sale listings (classiccars.com, dealer sites, auction pages) of cars in the named factory colour, original or correct repaint, daylight or neutral studio light. Flash and strong sun clip bright colours (reds, yellows), grass/sky reflections tint silver: judge each in the report, and send the user the report before applying.

## Recolor preview (optional per car)

A car with a `hero` block in `car.json` (`photo`, `mask`, optional `roof` hex, `credit`, `credit_url`) gets a floating car preview: greyed out with a "?" until the user clicks a filament swatch, then recoloured live in the browser (canvas, CIELAB: the photo's lightness variation around the body mean is kept, a/b come from the filament hex). `mask` is an RGB PNG the same size as the photo, one paintable area (zone) per channel: R = body paint, G = roof paint, B = a third area (soft edges); everything else (chrome, tyres, glass) is never touched. One photo + one mask per car; no `src/` change to add one. `roof` fixes the roof colour (two-tone cars); without it the roof follows the body. `prepare_hero.py` embeds both at 1000 px. The Doppler hero is a 3D Sets Model 23 photo used with their permission (`cars/doppler/sources/hero.jpg`, credited in the preview).

**Slots (zones).** A car is not limited to one colour: `hero.zones` in `car.json` lists the slots the user can colour separately, `[{id, label, channels: [0|1|2], fixed?}]` (`prepare_hero.py` documents the fields and writes them to `hero.json`; without `zones` a car has body + roof and one colour, like Torq and Sakura). A plain pick on the page colours every slot (a `fixed` slot, Doppler's white roof, goes back to its own colour); the hover bubble of a filament has "Put on" buttons, one per labelled slot, when the car has more than one. To make a slot, put its share of the body into its channel with `zones: {"<id>": {"channel": 2, "shape": <shapes dict>}}` in `hero_assets.json` (`make_hero_assets.py` moves the part of the body alpha inside the shape; marks of the same id in `hero_marks.json` force an area into it). Doppler: upper body (R), roof (G), lower body (B) = below the chrome line, ending at the front wheel arch (the nose ahead of the arch has the upper colour). The root-page tile treats R + B as the body.

**Factory combinations (`cars/<car>/combinations.json`).** Per year the two-/three-tone combinations printed on the cards, `{year: {source, note, combinations: [{code, upper, lower, intermediate?, unresolved?}]}}` with the card's own colour names. `build_html.load_combinations` shows a "Factory two-tones" strip under the year heading for entries whose colours are all paints of the car and whose slots the car has; hovering shows the car in that combination and the filament picked for each colour; a click sets upper and lower to the best PLA filament of those colours (the roof keeps its colour, white for Doppler, until set by hand) and shows only the rows of those two colours, even when one is on another year's card (1957 Frost White is the 1956 chip); clicking the active two-tone again shows everything. Entries with `unresolved` (a colour that has no chip on any scan, such as Ebony Black, Lipstick, Green Gold, Burgundy Maroon, Corinthian Cream) are kept for later and not published; so are those with an intermediate colour (1956-57), because Doppler has no such slot. Colours that exist only as chips on another year's card but appear in combinations (Toro Red, French Gray, Bali Blue, Admiral Blue) are normal paints of the car (`card_layout.json`, `box_width`/`box_height` per swatch).

**Preparing a hero (do this for every new car, it is what makes the recolor look clean).** Whatever the mask misses stays in the original paint colour (edge halos, specular rims, pink reflections in the glass, orange side-markers), so the original photo is made colour-neutral first and the mask is only a second step:
1. Use the largest original of the product photo, never the WordPress thumbnail (`…-900x600.jpg` → strip the size suffix; Sakura went from 900 to 1900 px, which matters). Save it as `cars/<car>/sources/hero.jpg` and never overwrite it.
2. Write `cars/<car>/hero_assets.json` (fields documented at the top of `src/make_hero_assets.py`): `hue` = Lab hue angle of the photographed paint (orange 45, red 35, green 155; measure the median hue under the mask), `glass` polygons (windows and interior, neutralised and never painted), `never_paint` shapes (headlight lens), `keep_color` rects (turn-signal lenses that should stay orange). Coordinates are in pixels of a `ref_width`-wide photo.
3. `python src/make_hero_assets.py --car <car>` writes `sources/hero_neutral.jpg` (paint chroma removed, lightness kept) and, with `"mask": "chroma"` (the default for every car: Sakura, Doppler, Torq), also `hero_mask.png`: the alpha is computed from the paint's own colourfulness, so edges are soft without hand drawing and nothing but paint-coloured pixels is ever recoloured. Pastel paints (Doppler's mint green) need a lower `mask_chroma` ramp, e.g. `[3, 10]`; a two-tone car gives `roof_shape` (a single-channel PNG, white = roof, kept in `sources/`) and its roof alpha goes to the G channel. `"mask": "keep"` is the fallback for a hand-made mask: it is left alone and only pixels within `grow` px of it are neutralised (`"grow": "all"` = whole photo). Changing a mask never needs per-colour images: the browser recolours from the one photo + one mask embedded in the page, so only `prepare_hero.py` + `build_html.py` of that car have to be re-run.
4. Point `hero.photo` in `car.json` at `sources/hero_neutral.jpg`, run `prepare_hero.py` + `build_html.py`, and look at the result with a blue, a white, a black and a cream colour (each leftover of the old colour shows up immediately). Fix by editing `hero_assets.json`, not by touching the code. `python src/review_hero.py --port <uncommon port>` is the review and mark-up tool for all cars at once (neutral photo, mask, overlay; zoom, pan): the user points at errors (W click-select: the connected area of similar colour around the click, with a tolerance slider; B box; L loop), typed `never` / `paint` / `roof` / `neutralise` / `keep`, which are saved at once to `cars/<car>/hero_marks.json` (polygons or wand clicks `{seed, tol}` in pixels of `hero.jpg`) and merged by `make_hero_assets.py` on top of `hero_assets.json`; its Rebuild button re-runs the three steps for that car. To fix reported errors read `hero_marks.json`, never hand-edit the masks.

## Root-page tiles: new-car recipe and what we learned

**Recipe for a new car's tile** (nothing in `src/` changes):
1. The car needs `hero` (photo + recolor mask, see above) and a built `data/matches.json`/`hero.json` (`rebuild.sh`).
2. **Cut the car out:** `.venv/bin/pip install "rembg[cpu]"` once (optional dependency, not in the build), then `.venv/bin/python src/cut_car.py --car <name>`. It runs the `isnet-general-use` model (`~/.rembg/models/…`, 179 MB, downloaded on first use, **not in the repo**; the committed result is what the build uses) and writes `cars/<name>/sources/cut_work/maska_rembg.png` plus previews on a yellow and a white tile. Look at the previews, then copy the mask to `cars/<name>/sources/hero_cut.png` (committed; grey = opacity, used as drawn). Window glass: by default it is cleared (tile colour shows through). `--glass-veil 0.3` keeps a pale veil of the glare, `--glass-veil 1` leaves the windows exactly as the model cut them (Torq uses this: the user preferred white windows). `cut_work/` is scratch, not committed.
3. `index.color` in `car.json` (the resting colour, the user's pick), tile look in `themes/<name>/tile.css` + `tile.html` (+ `tile-fonts.txt` for tile-only Google fonts), `src/build_index.py`, check hover on desktop and tap at 375 px, commit `site/index.html` and the mask.

**What we learned (don't redo):**
- *Cut-out quality.* Hand-made heuristics (flood fill from the border + closing + "grey = shadow") left white teeth on every edge, ate tyre lettering/hubs, and kept hard grey shadow patches. A neural matte (`rembg`) is clean on both cars. The automatic cut in `build_index.silhouette` is only a fallback; `hero_cut.png` wins.
- *White fringe.* Edge pixels are car+studio-white blends. `silhouette()` therefore ships a second photo (`fg`) where everything outside the eroded car takes its nearest car colour (`_bleed`), and the car layer is drawn from that. Keep this, or fringes come back.
- *Multiply alone cannot put the car above the border* (it darkens against it); the alpha cut can. The floor shadow is not part of the cut (the model drops it) and is redrawn by the multiply layer.
- *Glass.* White studio glare inside windows reads as opaque white on a coloured tile; clear it or veil it (see `--glass-veil`).
- *Tile styling tricks* (Doppler tile as the model): copy shapes from a reference by measuring its contour (the teal bubble is an SVG data-URI background stretched with `preserveAspectRatio="none"`, `vector-effect: non-scaling-stroke`), not by eye. A white outline + hard black shadow on a shape = `filter: drop-shadow(...)` on a **pseudo-element** (a `filter`/`transform` on the heading would become the containing block of the stretched link `::after` and break the whole-tile link); on a clipped ribbon use two pseudo-elements (white one slightly larger, red one) and put the `drop-shadow` on the unclipped parent, because `clip-path` clips its own filter. Titles are split into one `span.ch` per letter (`--i`, `--n` set by `build_index.split_name`), so a theme can bend/tilt them with `calc()`; words stay `nowrap`. The 8-point sparkle star is generated (cardinal tips longest, diagonal tips shorter, quadratic curves through a control point very near the centre = needle-thin middle, white stroke outline behind the fill); a thick middle looks wrong.
- *Layout.* Tile max width 470 px; the car overflows ~10 % each side; the foot's `padding-top` reserves the car's height (more on mobile); the swatch next to the filament name was removed on purpose. A theme's stripe/decoration must stay inside the black border (`left: 0`, not `-4px`).
- *Neutral tile backgrounds* are the default; Doppler's is warm cream (`#f5e8bd`, like the 3D Sets banner), Torq's `#f7f7f8`.

**Layout editor for tiles (`?edit`).** Run the preview with `.venv/bin/python scripts/serve_preview.py site 8765` (a no-cache server; plain `http.server` lets Chrome keep an old page) and open `http://localhost:8765/?edit`: drag a tile element (title, ribbon, date, label, button, stars, shield; Shift+drag = the car) or select it and use the arrow keys (Shift = 10 px), resize it (`+`/`-` keys, the panel buttons or Alt + mouse wheel), rotate it (`[` / `]`, Shift = 5°), pick colours (tile background, text colour of the selected element), then press "Uložit". Position and size are written as `translate`/`scale`/`rotate` rules to `themes/<theme>/tile-offsets.css` (all widths) or `tile-offsets-mobile.css` (when the window is <= 520 px wide at save time), colours to `tile-colors.css`, and `src/build_index.py` is re-run; `build_index.offsets_css` appends all of them after the theme CSS (so they win over `tile.css`). The panel can be dragged by its title and folded with the ▁ button. Don't fight the CSS with negative margins to nudge things: an `inline-block` with a negative `margin-top` stops moving after a few px (the line box clamps it), which is why the Doppler ribbon is `display: block; width: fit-content`. Saving is accepted from localhost only.

**Recolor mask (`hero_mask.png`, R = body paint, G = roof): what we tried to improve it.** The hand-made mask is good on the paint but leaks onto the dark interior seen through the windows and a few window-frame edges (visible when recoloured). `rembg`'s `isnet-general-use` only separates car from background, so it cannot help. Tried and measured on Doppler and Torq: (1) `src/refine_paint_mask.py`, a paint-hue/chroma test, small gain; (2) **SAM** (`new_session("sam")`, vit_b, ~375 MB in `~/.rembg/models/sam`, ~10 s per car on CPU) through `src/sam_paint_mask.py`, which drives rembg's encoder/decoder directly (encode once, decode many prompts; rembg's own `remove(..., sam_prompt=...)` re-encodes every call and unions all masks). **SAM alone is worse than the existing mask**: with one prompt it drops dark/glossy paint (Torq's shaded door, Doppler's door-seam reflections); prompted cell by cell (`--mode cells`) it leaks onto tyres, glass and bumpers. What works is `--mode zone` (default): SAM + hue test + darkness test trim the mask only in a band around the windows (window_zone), everything else stays as hand-made. Gain is modest (Doppler window streaks gone, a few blotches remain in the small rear window), so the result is written to `cars/<car>/sources/cut_work/hero_mask_sam.png` and is **not** applied automatically; to use it copy it over `hero_mask.png`, run `prepare_hero.py` and rebuild the car HTML and the index. Don't expect a prompt-only segmenter to beat a hand-made paint mask; the remaining fix is to repaint the few leak spots by hand.

## Non-obvious details

**Publishing: build locally, CI only deploys.** This repo is the single source and the GitHub Pages site (`https://martincollar.github.io/car-paint-filaments/<car>/`, public repo). `filaments/sources/` is gitignored, so CI cannot rebuild: HTML is built locally and committed in `cars/<car>/output/`. On push, `.github/workflows/pages.yml` runs `scripts/build_site.sh`, which copies each car with `"publish": true` in `car.json` to `_site/<car>/index.html` (+ an `intl.html` redirect to `?region=int`) and copies the committed `site/index.html` to `_site/index.html`.

**Root page: one themed tile per car (`src/build_index.py` → `site/index.html`).** Built locally (needs each car's `data/matches.json` + `data/hero.json`), committed, run by `rebuild*.sh` and `publish.sh`; CI only copies it, so after publishing a new car or changing `index` in `car.json` rebuild and commit `site/`. Each published car gets a tile in its theme's look: `themes/<name>/tile.css` (all selectors scoped `.tile--<name>`, never global) and `tile.html` (decoration positioned absolutely so it can spill over the frame; use unique SVG ids, the page holds several themes). A theme without them gets the neutral default tile. The car is the hero photo recoloured in the browser (same CIELAB code as `HERO_JS`) in two layers: the cut-out car (alpha from the cut, `z-index: 4`, above frame, text and decoration, so it can overflow the border) and the photo's own floor shadow (`.tile-shade`, the photo with the car painted white, `mix-blend-mode: multiply`, so the shadow stays soft and takes the tile colour). Never put `z-index`/`isolation`/`transform`/`filter` on `.tile` itself (it would stop the multiply reaching the page). Details and lessons: next section. Palette per car (`pick_palette`): primary first, then the best-ΔE filaments of all regions, deduped by hex and by ΔE ≥ 12 spacing, ≤ 8 colours. `"index": {"paints": ["Lemon Twist", "Basin Street Blue 1973", ...]}` in `car.json` (the user's pick, in cycle order, first = resting colour) cycles through the best **PLA** filament of each named card paint (`build_index.named_palette`; a trailing year picks one chip when the name repeats across years, otherwise the closest match wins). An entry may be `{"combo": "RQ-144"}`: a factory two-tone from the car's `combinations.json` (upper colour on the R zone, lower on B; each colour its best PLA); `"roof": "upper"|"lower"|"white"|"#RRGGBB"` on the entry picks its roof, otherwise the roof keeps `hero.roof`. `scripts/tile_combos.py` is the visual tool to order, drop, add and set roofs (writes `index.paints`). `"roof_upper": true` in `index` paints the roof in the upper colour instead of `hero.roof`; `"shuffle": true` shuffles the hover order on every visit (the first, resting colour stays first). Without `paints`, optional `"index": {"color": "#RRGGBB", "order": 10}` in `car.json`: `color` is the colour the tile rests on (pick one that differs from the 3D Sets original; default = best match), `order` sorts tiles (default 100, then by name). The car's cut-out comes from `cars/<car>/sources/hero_cut.png` when it exists (grey mask, white = car, grey = partly clear, used as drawn; made by `src/cut_car.py --car <name>` with `rembg`, which also clears window glass), otherwise from the automatic cut in `build_index.silhouette` (flood fill from the border; good, but leaves faint patches under the body). Mouse: hover cycles colours and the whole tile links to the car; touch: a tap on the car shows the next colour, the title and button open the car.

**`color_tools._load()` must composite transparent PNGs over white before converting to RGB.** PIL's `.convert("RGB")` on a palette PNG with a `transparency` entry returns the first palette color (often green or black), not the actually rendered pixel. Several e-shops ship photos in this format. Any new image-reading code must go through `_load()`, not call `Image.open(...).convert("RGB")` directly.

**`filament_rgb()` branches on average saturation after filtering.** Colored filaments use the saturation²-weighted dominant hue of pixels within ±15° of the peak, excluding studio-white background, dark brown cardboard (hue 15-45° at v < 0.65), yellow Smart3D watermarks (hue 42-62° at s > 0.4, but only when that yellow is < 4 % of the foreground — otherwise it *is* the filament; before this rule every yellow filament measured near-black) and gray pixels (s < 0.10, whose "hue" is numerical noise). The colour path needs colourful pixels to be > 2 % of the measured ones (not just > 200), or anti-aliased edges of a removed spool flip a pale winding to "coloured". Neutral filaments fall back to the median of the remaining pixels, minus light kraft (boxes, spool cores) when ≥ 60 % remains and minus dark achromatic spool flanges when ≥ 30 % remains. Changing any threshold shifts many colours at once: **before every measurement change, re-measure the whole cz catalogue against the current `filaments.json` and look at a photo/old/new sheet of everything that moved ΔE ≥ 3** — several plausible-looking fixes this session broke dark browns, blues or tan filaments elsewhere.

**Name hints (`filament_rgb(name=...)`).** `measure_filaments.py` passes the colour name. `neutral_class()` maps it to black / dark (antracit, graphite, tmavě šedá) / white / grey (incl. silver, hliníková) and then measures only dark / v < 0.5 / lit-half light / mid-grey low-saturation pixels with kraft excluded (grey also drops white spool labels). `kraft_like_name()` (beige, brown, tan, gold, pink, peach … families) gates the **kraft second pass**: when > 12 % of the photo is light cardboard and the result is cardboard-coloured but the name is not a cardboard-like colour, the whole brown hue band is dropped and the photo re-measured — accepted only if ≥ 5 % of the foreground remains and the result isn't the black spool (protects tan filaments with unknown names, e.g. Fillamentum "Mukha"). The saturation filter that keeps only strongly saturated pixels in the hue window (orange next to a kraft box) runs only when p90 saturation ≥ 0.75 *and* the photo has kraft; elsewhere it darkened blues by dropping highlights.

**Per-brand hints: `measure_hints` in `shops/_defaults.yaml`** (brand regex → `filament_rgb()` kwargs). Use them when one brand's photos share a prop that defeats the generic rules: `aurapol: {min_chroma: 0.06}` (slightly bluish black spool outvotes pastels; not global because dark bronze/olive have the same tiny chroma), `sunlu: {drop_hue_band: [205, 240, 0.05, 1.0]}` (blue-grey spool with a navy hub). Prefer a hint over a code special case, and an override over a hint for single items.

**`src/review_sheet.py` is the visual check** (`--material ASA`; served by default, `--no-serve` = static page without the reason boxes; click a card to mark it wrong; each card also shows the pixels `filament_rgb()` used (dimmed = ignored) and a ▣ sample button: drag a square over clean winding and save its colour as an override; `--unsampled` hides cards fixed that way) (`filaments/.cache/review_sheet.html`, opens in the browser): photo next to measured colour, a "Changed by the last measurement" section (`previous_hex`, set by `measure_filaments.py` when a colour moves ΔE ≥ 3), and flags `box` (kraft photo whose result looks like cardboard and name isn't beige/brown) and `cluster` (3+ names of one brand measuring the same). Run it after every measurement or catalogue change; the user reviews colours there. **Always start it yourself in a Terminal panel tab (`run_in_terminal`, e.g. `--brand <brand> --serve --port 8766`) and give the user the clickable URL to open (`http://localhost:<port>/`) in your reply; never just point at the HTML file or say it was regenerated.**

**`filament_rgb()` cannot always measure white or black filaments, and darkens shaded renders.** Without a name hint a white winding is indistinguishable from the studio background (V > 0.93, S < 0.08) and a black one falls under the shadow cut (V < 0.15), so the median lands on the spool, stand, label or cardboard. Edge-connected background removal doesn't fix this: a white winding sits next to white or grey stands, and a black one next to black flanges. The hue-window median includes the filament's own shadows, so heavily shaded renders come out darker than the lit surface (Prusament Electric Green: #83C59D measured vs #BFEDCC lit). A global "brighter half" measurement was tested and rejected: it changed the primary pick for 44 of 65 Hudson paints and worsened best ΔE for 42 (the lit half is used only for white-named filaments and for hand-made overrides).

**White lift: names that say white are pulled towards true white.** A filament photo cannot show white lighter than ~#ECECEC (`filament_rgb()` drops v > 0.93, s < 0.08 as studio background) and the winding is shaded, so every white measured grey (#DB..#E9, hand-sampled ones #CA..#D2). Changing thresholds would move every colour, so `measure_filaments.py` applies `color_tools.lift_white()` after the overrides, to records whose name `neutral_class()` calls white. Rules: `white_lift` in `shops/_defaults.yaml`, an ordered list `{match, L, pull, chroma}` (first diacritics-folded regex hit on the colour name wins; `L` target lightness, `pull` share of the way there (0 = leave alone), `chroma` factor on a*/b*). Currently: ivory/bone/cream/vanilla/skeleton/špinavě/aluminium/lilac untouched; traffic/signal/dopravní pure #FFFFFF; cold/ghost/warm nearly white with a light cast; every other white ≈ #FFFFFF. The pre-lift value is `pre_lift_hex` on the record. To tune: edit the rules, re-run `measure_filaments.py`. **An override in `color_overrides.json` is lifted too** when its name says white (their hexes came from the same grey photos), unless the override says `"lift": false` (exact hex, kept as written: Aurapol ASA Signal White RAL 9003, Skeleton, Vanilla, Bambu); the white-named overrides carry `"lift": true` explicitly so each can be flipped later. The paint side has the same rule for chips that really are white: `"white": true` on a swatch in `card_layout.json` (`measure_car.py` lifts it, `measured_hex` keeps the scan/photo value). Used for Sakura Kilimanjaro White and Torq Sno-White only: photos of white cars read #D0..#E0 and would otherwise match grey filaments; cream paints (Ivory, Spinnaker, Frost White) are not flagged. `calibrate_car.py` entries can carry `"basis": "lit"` (suggest from the brighter half instead of the median) for white/beige paints.

**Neon filaments are flagged and ranked behind normal ones.** `neon_names` in `shops/_defaults.yaml` (diacritics-folded regex on colour name and slug: fluo, neon, UV, highlight, "super yellow") makes `measure_filaments.py` stamp `neon: true`; `compute_matches.topk()` ranks them as ΔE + `NEON_PENALTY` (8; the shown ΔE stays real) unless the paint's own Lab chroma is ≥ `NEON_PAINT_CHROMA`; the page shows a NEON tag (`.neon-tag`). Why: neon looks wrong on a car, and their photos measure too dark (shaded sides pull the median down: 3DFOX Žlutá FLUO stored #C5C700, lit #E7F100), so plain ΔE made them win lime paints. Add a keyword to `neon_names` rather than a slug list.

**Finish flags and the page's finish toggles.** `finish_flags` in `shops/_defaults.yaml` (name → diacritics-folded regex, Czech and English, run on colour name + title + slug) makes `measure_filaments.py` stamp `finish: [..]` on every record: `glitter` (glitter, sparkle, galaxy, metallic/metal/metalická, třpytivý, stardust, starlight, star, glamour, brillant, diamond, aurora, shimmer, sugar, pearl/perleť/perlová, iridescent, chameleon, flip, vertigo), `matt` (mat, matt, matte, matná, soft touch, velvet, suede) and `satin` (satin, satén, satyn, semi/half/polo-matt). `matov*` is deliberately not a matt keyword ("mátová" = mint folds to it), and bare metal colour names (copper, gold, silver, bronze, hliníková) are not flagged. Add a keyword to the regex, never a slug list, then re-run `measure_filaments.py` (colours do not change) and `tests/test_shoplib.py`. The page header card has a "Finishes:" toggle group (one button per flag, `data-finish-btn`, `body[data-finish]` = pressed set like `glitter+matt`, `-` = none, `?finish=glitter,matt` in the URL). A filament with a flag that is not switched on is out of the candidate pool, so every toggle state has its own top-k: `compute_matches.match_colors()` per state, `build_html.render(variants=...)` emits one `.rcols[data-f~=state]` block per distinct result (page size roughly doubles: Torq ~8 MB). `matches.json` (and with it the root-page tiles) holds the car's default state only. Per-car default: `"filter_defaults": {"glitter": false, "matt": true, "satin": false}` in `car.json` (missing = all off, so an army-style car turns `matt` on). Rows and the hover bubble show a GLITTER / MATT / SATIN tag (`.finish-tag`).

**Manual colors go in `filaments/color_overrides.json`** (`{slug: {hex, note}}`, path in `config.FILAMENT_COLOR_OVERRIDES`). `measure_filaments.py` applies them after measuring, sets `confidence: "manual_override"`, keeps the measured value as `measured_hex`, and warns about override slugs that no longer exist. After dedup it also prints `! suspicious measurement` for any measured record whose name says white/black but whose lightness contradicts it (L < 75 / L > 30). Treat each warning as a to-do: crop the winding in the photo, take the median, add an override with a `note` saying where the hex came from. Transparent filaments (e.g. Fillamentum PETG Natural) can't be measured from a photo at all; leave them alone rather than guessing.

**ΔE2000 weights lightness over hue.** A bright yellow may score numerically closer to a beige than a muted peach does. In the HTML, the primary candidate is always shown; up to 4 alternatives follow when their ΔE < max(10, primary + 2), and a red "no close match" banner sits above a primary with ΔE ≥ 12 (`NO_MATCH_DE`). Don't change either threshold without visually inspecting the resulting pairs.

**Shops are discovered from sitemaps, filtered by rules, and reviewed through a lockfile.** `fetch_all.py` reads each shop's sitemap, keeps URLs matching `include` and none of `exclude` (`_defaults.yaml` + shop) whose path names PLA/PETG/ASA, then reads each product page. Rules, not code, keep out the noise: samples, bundles, 2.85 mm, 3+ kg, CF/GF/wood/glow, multicolour/thermo, other materials. **ASA** is matched like PLA/PETG (`config.ASA_MATERIALS`, `rec["asa"]`). Each paint row on the car pages is the original colour full width on top, then three equal columns PLA | PETG | ASA (`.row > .paint-col { grid-column: 1 / -1 }` in every theme). `pins:` are hand-written products. On `manual` shops (Prusa3D, Na3D) they are the whole catalogue; on the others they are the old per-script slug lists, migrated, and discovery finds them anyway — the pin only keeps brand/material/color_name/local_image (and so the measured colour) stable. Pins skip include/exclude and the title check (not the finish ban), so never pin something the rules would reject (2.85 mm, 0.5 kg, HT-PLA as its own material); `overrides:` (by slug) fix a discovered item or `skip` it. Each run rewrites `filaments/data/catalog.lock.json` (accepted products + rejected slugs with reason); **review its git diff before rebuilding**, that's where new and vanished filaments show up.

**One brand sold by several shops: preferred shop wins.** `measure_filaments.drop_duplicate_listings()` dedupes across shops only for brands in `preferred_shop` of `shops/_defaults.yaml` (brand regex → shop name; currently `^aurapol$` → Aurapol, because Smart3D resells the same Aurapol PLA/PETG/ASA under Czech names with the same render). A twin = same brand + material and measured colour within `dedupe_delta_e` (2), paired one-to-one nearest first, so a colour only the other shop stocks stays (except materials in `preferred_shop_exclusive`, currently ASA: every other shop's listing of that brand goes, Smart3D and Hubacek only resell it); the other shop's record is dropped before overrides run, so **put overrides on the preferred shop's slug** (an override for a dropped slug is reported as unknown). The generic dedup stays `(url, slug)`; other brands keep every shop on purpose (each shop link is a real choice), add one line to `preferred_shop` to change that.

**Banned finishes: transparent, natural, silk, marble/stone, lightweight (LW-PLA, Poly Light).** The user never prints with them. `exclude_finishes` in `shops/_defaults.yaml` (diacritics-folded regexes, so "průhledná", "čirá", "přírodní", "hedvábná" match) is applied to slug, URL, title and colour name of every record — pins included — in `fetch_all.py`, and again in `measure_filaments.py`. Don't pin or override one back in.

**Fetching is polite and loss-free.** `shoplib.http_get()` obeys robots.txt `Disallow` and `Crawl-delay` (min 0.5 s, cap 20 s per host), retries 429/5xx with backoff, and caches bodies in `filaments/.cache/` (gitignored) with ETag/Last-Modified. Known pages are re-read only after `refresh_days` (7) unless the sitemap `lastmod` is newer; never-seen pages are capped by `max_new_per_run` (300), so the first crawl of a big shop spreads over runs (`--max-new N` overrides). A page that errors keeps its previous record with `stale: true`; a 404, or a redirect to a non-product page (3DJake sends dead slugs to search, whose og:image is the shop logo), drops it. A shop whose record count would fall below `min_keep_ratio` (80 %) is not written (`--force` to accept). Availability comes from schema.org markup, not from grepping "Skladem" (which appears in every page's menu). Product names come from JSON-LD/`<h1>` before og:title, and `clean_title()` strips promo prices ("jen za 298 Kč") and emoji.

**One theme folder per car, light-only.** The page's whole look lives in `themes/<name>/` (`theme.css` = every style incl. `:root` variables, `fonts.txt` = Google Fonts query, `motif.html` = decoration injected in the header); `build_html.py` holds markup only. `car.json` picks one with `"theme": "<name>"`; a car without `"theme"` gets `default` (plain grey, IBM Plex Sans, one graphite accent; a new car needs no theme folder unless it should look different). Themes share class names, not styles, so a car with its own look is a new folder, never a change in `src/`: copy `themes/default` (or `doppler`) and rewrite. `doppler` is the mid-century cream/teal/mustard look (set explicitly in its `car.json`), `torq` the 1970s red/navy shield-and-stripes one, `sakura` the "Sakura Run" poster one (cream paper with print specks, black ink, blossom pink, striped red-pink sun, cherry branch and kana sign; see `themes/sakura/DESIGN.md`). The recolor preview and hover bubble follow the same rule: `build_html.py` (`HERO_CSS`, `TIP_CSS`) holds layout and states only, while each theme styles `.hero-preview`, its `.hp-close`/`.hp-zoom` buttons (icons via `::before { content }` or background), `.fil-tip` and defines `--hero-q-bg/--hero-q-fg/--hero-q-font` (the canvas "?" placeholder reads them). A theme must keep the `--teal/--orange/--mustard/--navy/--bg-raised/--rule/--muted/--font-display/--font-mono` variables, because the shared recolor-preview CSS reads them. Each theme is a single light look: no `@media (prefers-color-scheme: dark)` or `[data-theme="dark"]` blocks. Years are listed newest-first in the main loop and in year navigation; keep that order.

**Design language per car (`themes/<name>/tokens.css`, `DESIGN.md`, `styleguide.html`).** Each car's look is one set of `--dl-*` variables (colours, fonts, shadow, radius), scoped `.theme-<name>, .tile--<name>` so the root-page tile and the detail page share them; `tile.css` and `theme.css` read them instead of hard-coding hexes. The detail page header is a tile-style card (`tile_parts.head_card_html`, `tile.html` as decoration, `tile.css` + `headcard.css`) placed above the paper, with the region switch and year jump nav inside it; the ΔE scale legend lives in the footer. A theme without `tokens.css` keeps the old header inside the paper (no real theme does now; the test uses a temp one). `python src/build_styleguide.py --theme <name>` regenerates `styleguide.html` (tokens, fonts, buttons, header card, table row) after a token change. Each theme's `DESIGN.md` records the palette, shapes and the tile recipes. The header card has the same layout editor as the tiles: serve the worktree with `scripts/serve_preview.py . <port>` and open `/cars/<car>/output/<car>.html?edit`; "Uložit" writes `themes/<theme>/headcard-offsets.css` (`-mobile` at <= 520 px) and `headcard-colors.css` (selectors `.tile--<theme>.head-card ...`, loaded after `headcard.css`) and rebuilds that car's page. The page background is `--dl-page` (lighter than the card's `--dl-bg`); vertical spacing of rows and candidates is `SPACING_CSS` in `build_html.py` (all themes); the enlarged preview is capped to the viewport height.

**Visit counter (optional).** `config.GOATCOUNTER` (env var `GOATCOUNTER`, a GoatCounter site code) turns on `build_html.counter_html()`: the GoatCounter hit script plus a "Visitor no. N" line in the footer (`#vc`, styled per theme as `.visit-count`), read from `https://<code>.goatcounter.com/counter/TOTAL.json` (needs "Allow adding visitor counts" enabled in the GoatCounter settings). Default `mkolar`; empty = no script, no footer line. count.js itself ignores `file://` and localhost. It is our own stats script, not an affiliate/tracking code on shop links, so it doesn't conflict with `clean_url()`.

**Public naming.** Pages use `display` from `car.json` (Hudson's is "3D Sets Doppler", matching its preview photo), the real colour names and codes from the cards, and do **not** name or link the card library (`autocolorlibrary.com`): that host stays in code and data (`card_source_url`, `source_url`, fetch/measure scripts) only, never in generated HTML. Don't invent fictional car names or brands. What must stay out of published pages are third-party affiliate/tracking codes on shop links: `build_html.clean_url()` strips them.

**Thumbnails cost context in the HTML.** The page is self-contained with ~1-2 MB of base64 image data (both regions, so each candidate photo appears once per region it is shown in) (filament photos only); keep thumbnail max_dim at 100-200 px and quality 70-78, and never embed raw card scans. If size balloons unexpectedly, check for transparent PNGs being compressed poorly after the white composite.
